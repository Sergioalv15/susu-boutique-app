# Application audit — 2026-09-21

## Verdict

The application is a functional foundation for a controlled Android pilot, but is not ready for commercial distribution. Protecting restore operations and preserving financial inputs take priority over adding features. Android release signing needs production preparation; iOS device and distribution behavior remains unverified.

This is a source and automated-check audit of the current working tree in `C:\dev\appJorge`, including its uncommitted changes. No application code was changed during this audit. Findings describe verified code paths; they were not reproduced on a physical device in this audit.

## Prioritized findings

### 1. High priority: restore can replace live data before checking compatibility

`src/core/storage/backup.ts:75–84` copies a deserialized SQLite database over the live database without validating the application schema/version or migrating the candidate first. `src/core/storage/sqlite.ts:19` retains its initialized state, so migrations do not automatically run after replacement.

**Impact:** restoring a structurally valid older or unrelated SQLite database can replace the user's records and leave subsequent queries failing. There is no safe rollback in this flow.

**Change:** validate and migrate an isolated candidate; retain a recovery copy; confirm replacement; swap only after validation; reinitialize database consumers. Test corrupt, unrelated, older and newer-schema files on a disposable native database, proving the original data survives rejection or failure.

### 2. Financial correctness: editing changes a fractional margin

`src/features/daily-records/presentation/hooks/useDailyRecord.ts:30` rounds the stored proportion to an integer percentage. Saving through `src/features/daily-records/application/DailyRecordService.ts:15` persists the rounded value.

**Example:** a stored margin of 30.4% on sales of €1,000 becomes 30% when reopened and saved unchanged. Gross profit changes from €304 to €300, and calculated investment from €696 to €700.

**Change:** preserve supported decimal precision during form conversion. Add an edit-and-resave regression covering a fractional percentage and an unrelated field change.

### 3. Navigation: investment success can go back twice

`app/investment/purchase.tsx:43` navigates back and returns success. `src/features/daily-records/investment/presentation/components/InvestmentPurchaseModal.tsx:62` then invokes `onClose`, whose route callback at `purchase.tsx:59` navigates back again.

**Change:** give a single layer responsibility for closing the successful flow. Verify success and cancellation from the calendar and direct route entry.

### 4. Annual totals do not refresh on return

`src/features/daily-records/presentation/hooks/useAnnualSummary.ts:51` reloads when its year changes, without a focus refresh. A mounted annual screen can show old totals after a daily record is edited elsewhere.

**Change:** refresh on return and reject superseded responses. Verify annual summary → edit day → save → annual summary without changing the year.

### 5. Biweekly data can be overwritten by an older request

`src/features/daily-records/presentation/hooks/useBiweeklyRecords.ts:35–56` starts asynchronous loads and writes their results without checking whether the requested window is still current.

**Change:** invalidate superseded requests and prevent writes after disposal. Verify two window loads completing in reverse order.

### 6. Publication preparation: signing, versioning and repository credentials

`android/app/build.gradle:115` signs the local release variant with the debug signing configuration; its `versionCode` is 1 at line 95. The local `apk:release` script does not inherit the EAS production profile's remote versioning behavior. `credentials.json` and `@sergioalv15__appjorge.jks` are tracked by Git; their contents were not disclosed by this audit.

**Change before commercial distribution:** establish production signing and one versioning procedure; separate credentials from tracked source and assess actual exposure before deciding whether rotation or history remediation is required. Do not remove keys or rewrite history without a recovery plan.

Debug signing is acceptable for the user's private test APK; it does not itself block that requested test. Production readiness and private APK delivery are separate milestones.

## Product choices and strengths

- Calendar month changes clear selection; action buttons visibly fall back to today. This is a UX decision to improve, not a confirmed silent financial error. Prefer a deliberate date choice before registering an investment for another month.
- Transactional migrations already provide rollback during ordinary schema upgrades.
- Monthly calendar and holiday loads already guard against stale responses. The bounded holiday review found no additional definite high-priority defect; device behavior remains unverified.
- Financial calculations, state transitions and other pure logic have an existing automated test suite, providing a useful foundation for regression checks.

## Recommended next sequence

1. Preserve user data: safe restore and recovery behavior.
2. Correct fractional margins, investment navigation, annual refresh and biweekly races.
3. Run relevant regressions and Android device checks; generate a private test APK locally with the existing script.
4. Validate daily use with a small pilot; improve date selection, error messages and business customization based on observed friction.
5. Prepare production signing, versioning and actual iOS builds/device testing before store distribution. Validate demand before committing to a monetization model.

Changes above are recommendations, not implementations performed by this audit. The requested next phase is to define/apply fixes and deliver an APK; a PC filesystem link alone is not a mobile download channel.
